# Chap validation

Chap talks to one LewLM base URL and nothing else: no engine names, no engine
SDKs, no CUDA settings, no engine-specific SSE parsers. This page is the
contract Chap builds against, the backend proof that already exists for it,
and the UI checklist that is still pending. Backend correctness never waits
for the UI; UI acceptance is recorded separately and never silently marked
complete.

## Develop against LewLM with no model

```bash
python -m lewlm.testing.fake_backend --port 8080            # LewLM + a fake engine on 127.0.0.1:8080
python -m lewlm.testing.fake_backend --port 8080 --cors-origin http://localhost:5173
```

The fake engine answers by rule (echo, `count` → "one two three four five", a
tool call when a tool is offered, a schema-shaped object when JSON is
requested, a 200-word reply to any "long" prompt so cancellation has
something to stop). Every public route behaves as it does with a real bridge:
the model id is stable, capabilities are reported, streams end with a usage
chunk and `[DONE]`, cancellation closes the upstream connection, an engine
outage is a 503 naming the endpoint, a dying engine ends the stream with an
error envelope. What it cannot do is produce model-quality text; do not judge
rendering of long or formatted replies against it.

## Backend proof (exists, passes on every OS)

```bash
python examples/chap_backend_smoke.py --fixture --output chap-smoke.json     # CI runs this on Linux, macOS, Windows
python examples/chap_backend_smoke.py --base-url http://127.0.0.1:8080 --model <id> [--endpoint-id vllm]
```

| Check | What it proves |
| --- | --- |
| `service_health` | `GET /v1/health` is `ok` and carries `engines[]` separately from service status |
| `runtime_startup` | `GET /v1/runtime.startup` reports LewLM ready, engine state, warm models — without probing |
| `model_picker` | `GET /v1/models.capability_availability[]` names `chat_ready`, `reason`, `endpoint_id`, `engine_profile`, `engine_state`; `GET /v1/models/{id}/capabilities` predicts structured-output enforcement |
| `request_identity` | `x-request-id` and `x-lewlm-correlation-id` are echoed on the response and in `metadata`; `x-lewlm-application-id: chap` is accepted and grants nothing |
| `responses_finish_reason` | `POST /v1/responses` publishes `finish_reason` on its sync body from the chat vocabulary (`stop`, `length`, `tool_calls`), so a reply truncated by `max_output_tokens` is distinguishable on both surfaces; the fixture's long reply must be `length` |
| `chat_streaming` / `chat_nonstreaming` | one terminal chunk with `finish_reason`, honest `usage` (and `cached_tokens` when the backend reports it), `[DONE]` |
| `structured_output` | `json_schema` output validated after generation; `structured_output.enforcement` / `decoder_enforced` say what actually happened |
| `tools` | a native tool call arrives as `tool_calls` with parsed arguments; the tool-result continuation works |
| `reasoning` | hidden reasoning never leaks into visible content |
| `cancellation` | `POST /v1/requests/{x-request-id}/cancel` stops the stream; the stream ends with `finish_reason: "cancelled"` then `[DONE]`; a new request works |
| `failure` | an unknown model is `404 model_not_found`; health stays `ok` |
| `unavailable_engine` (fixture) | engine down → `503 runtime_unavailable` with `details.endpoint_id`; health stays `ok` with `engines[].state` `failed`/`stale`; the model stays listed; recovery after rescan |
| `stream_interrupted` (fixture) | engine dies mid-stream → HTTP 200 stream ending with `finish_reason: "error"`, an `error` envelope with `partial_output: true`, then `[DONE]`; never replayed |

Exact payloads for each of these are in `examples/integration-bundle.json`
under `chap.examples`, regenerated by `scripts/export_integration_bundle.py`;
`chap.field_notes` says which fields can be absent and what each state means.

## The three states Chap must show separately

| State | Read from | Never infer from |
| --- | --- | --- |
| Service up | `GET /v1/health.status == "ok"` | an engine being reachable |
| Engine reachable | `health.engines[].state` / `runtime.startup.engines[].state` (`advertised`, `stale`, `failed`, `unknown`) and `capability_availability[].engine_state` | HTTP 200 on health |
| Model warm | `runtime.startup.warm_models[]` / `GET /v1/runtime/residencies` | a model being listed |

## UI checklist (pending)

Record each item as `passed`, `failed`, or `pending` with the LewLM version,
the backend (fixture or engine + model), and the browser/OS. Do this against
the fixture first, then against a real engine recipe.

| # | Item | Expected behaviour | Status |
| --- | --- | --- | --- |
| 1 | Model picker | Lists `chat_ready` models with their `engine_profile`/`endpoint_id`; a model with `engine_state: failed` or `chat_ready: false` shows its `reason` and cannot be selected for chat | pending |
| 2 | Capability-driven controls | JSON-output and tool controls are enabled only when `GET /v1/models/{id}/capabilities` advertises them; the predicted `structured_output` enforcement is shown before sending | pending |
| 3 | First-token rendering | The first `delta.content` renders as it arrives; role-only chunks render nothing; `: keep-alive` comments are ignored | pending |
| 4 | Stop button | Sends `POST /v1/requests/{x-request-id}/cancel` with the same handle the request used; the UI shows "stopped" on the `finish_reason: "cancelled"` chunk, keeps the delivered text, and re-enables input after `[DONE]` | pending |
| 5 | Tool deltas and results | `delta.tool_calls[]` fragments are concatenated per `index`; the parsed `tool_calls` on the terminal chunk drive the tool UI; the tool result is sent back as a `tool` message | pending |
| 6 | JSON display | `structured_output.parsed_output` is rendered when `validation.state` is `valid`; otherwise the raw text and the validation message are shown | pending |
| 7 | Usage | `usage` from the terminal chunk only; `measured: false` is labelled as an estimate; `cached_tokens` is shown only when present | pending |
| 8 | Engine restart | Stop the engine: chat fails with a 503 naming the endpoint, the UI keeps the model listed and marks the engine failed; restart + rescan: the UI recovers without a reload | pending |
| 9 | Interrupted stream | Engine killed mid-stream: the UI shows the partial text, the `error.message`, and offers a retry the user must choose; nothing is replayed automatically | pending |
| 10 | Fallback explanation | When `metadata.routing.fallback_from_model_id` is set, the UI says which model actually answered and why (`fallback_reason`) | pending |
| 11 | Identity headers | Every request sends `x-lewlm-application-id: chap`, a unique `x-request-id`, and the conversation's `x-lewlm-correlation-id`; the echoed values match | pending |
| 12 | Browser origin | Chap's origin is in `LEWLM_CORS_ALLOW_ORIGINS`; preflight and SSE responses carry it; `x-request-id` is readable from the browser (`cors_expose_headers`); no wildcard is configured | pending |

The backend side of items 1–12 is covered by `tests/integration/test_chap_contract.py`
and the smoke script above. Fill this table in Chap's own repository against a
tagged LewLM version; keep it out of LewLM's release evidence until it is.
